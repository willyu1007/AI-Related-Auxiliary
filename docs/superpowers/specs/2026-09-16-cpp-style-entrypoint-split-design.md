# C++ 规范技能命令入口分离设计

## 目标

将 `cpp-code-style` 和 `cpp-code-style-manager` 的命令入口与职责分离，使日常技能只负责读取有效规则并检查 C++，管理技能负责规则生命周期和所有写入操作，同时保证现有用户数据无需任何迁移。

## 设计决策

本次不引入第三个公共 core 技能，也不让两个技能互相导入脚本。两个技能各自维护自己的脚本实现，通过仓库内固定的数据契约、路径约定和共享测试夹具保持同步。

命令入口放在各自技能目录：

```text
system/skills/cpp-code-style/scripts/style.py
system/skills/cpp-code-style-manager/scripts/manage.py
```

`cpp-code-style` 的入口只提供日常能力：

- 查询 effective 规则的精简元数据；
- 查询 effective 规则详情；
- 对用户明确指定的 C++ 文件执行检查和支持的格式化。

`cpp-code-style-manager` 的入口提供管理能力：

- 初始化状态和完整层级校验；
- 规则来源、层级链和覆盖解释；
- 有效格式配置导出；
- profile/组织规则导入、升级、提案和应用；
- 规则启用、禁用、取消覆盖及其它持久化修改。

日常入口不公开层级参数、写入参数、来源字段或管理命令。`enabled`、层级和 `overrides` 仍由日常实现读取并参与有效规则计算，但不作为日常技能的展示内容或写入职责。

## 数据兼容边界

以下内容必须保持不变：

- `rules.yaml`、`details/*.yaml` 和 `organization.yaml` 的路径；
- `schemaVersion`、profile、organization、rules 及现有规则字段；
- detail 文件格式和规则 ID；
- 层级合并、同 ID 替换和 `overrides` 语义；
- 系统、用户、组织和项目数据的现有内容。

本次不得执行数据迁移、字段重命名、序列化格式转换、自动重写或目录迁移。现有 `rules.schema.json` 继续作为仓库级数据契约使用，不改变其内容。

## 实现边界

从当前集中式 CLI 中移除管理命令的日常入口，将管理相关实现归入 manager；保留日常检查所需的规则读取、effective 合并和 handler。由于 CLI 不要求兼容，旧的集中式命令分发方式可以直接替换，不需要兼容转发层。

两个技能的脚本可以各自保留必要的规则读取和校验代码，但不得通过复制后随意改变数据语义。任何数据契约变化都必须同时更新两个技能的实现和共享测试夹具。

## 验证要求

测试必须覆盖：

1. manager 写入的现有格式数据可被 style 读取；
2. style 仍按原有层级规则得到相同 effective 规则；
3. style 只展示启用规则的 `id`、`summary`、`appliesTo`；
4. style 不执行任何规则写入；
5. manager 的提案、应用和组织绑定行为保持原有结果；
6. 用户数据目录在完整测试前后不会被修改。

## 非目标

- 不改变规则数据模型；
- 不重新设计规则合并算法；
- 不增加公共 core 技能或运行时包；
- 不保留旧 CLI 命令兼容；
- 不扩大到全仓格式化、构建或外部规则学习。
