# 来源归一化

当用户提供官方网站 URL、本地文件或文档时，应将其作为来源材料进行解释，并生成临时的候选 YAML 供审查。不得将来源文档复制到规则存储中。

每份归一化报告必须包含以下三个审查列表：

1. 纳入的规则：每条都包含具体内容、适用范围、强制程度、来源章节和执行能力。
2. 排除的材料：说明每项排除的原因。
3. 未决的决定：必须在写入前得到回答。

归一化时先将来源拆分为细粒度候选规则：一条候选规则只包含一个可独立确认、启用、禁用、覆盖和审查的规范意图，并指向一个主要对象和清晰范围。来源段落中多个可以分别判断的要求必须拆成多个规则 ID，即使它们来自同一章节。

`summary` 只描述一个结论，`appliesTo` 应尽量具体，`detail` 只保存该单一意图的条件、例外、示例和判断依据。不能因为要求来自同一段文字，或多个对象都属于“命名/布局/注释”，就合并成一个宽泛规则。拆分后发现范围相近时，保留不同 ID，交由 runtime 技能按 ID 和 `overrides` 判定关系；归一化流程不得自动合并规则或生成覆盖声明。

未决内容不得写入，也不得静默降级为 advisory。候选数据在系统 `profile.sources` 中记录来源定位和获取日期；规则级 `source` 标识具体章节。CLI 负责校验 Schema、详情、路径、差异、digest 和过期目标；AI 负责解释来源并与用户沟通。

候选文件和提案 JSON 应放在临时目录中，对话中断后可以重新生成。自定义系统规则集存放在用户系统数据目录下，由用户自行维护；它不会被 bundled 规则包目录自动替换。
